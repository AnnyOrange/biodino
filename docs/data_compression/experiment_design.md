# 7B DINO 数据压缩实验设计

## 背景

现有数据从 1PB 经过去重后形成了 100TB、10TB、1TB 三个版本。目标训练数据预计是 10TB 或 100TB，用于训练 7B 规模 DINO 模型。但训练机器本地存储不足以直接容纳 10TB 数据，因此需要验证压缩或数据蒸馏方案是否可行。

存储目标：训练侧没有给硬上限，只要求“在公司服务器上尽量小”。这有两个直接影响：

1. 没有可以 early-stop 的具体阈值，因此**有损压缩和数据蒸馏从一开始就在方案范围内**，不能只做无损就收工。
2. 评估标准从“能否塞下”变成“在可接受的 benchmark 下降内，能压到多小”。每个方案都要同时给出压缩率和 benchmark 代价，才能在 size–quality 曲线上取点。

当前建议先在 1TB 数据集上做可控实验，评估不同压缩策略对预训练和下游 benchmark 的影响，再决定是否扩展到 10TB 或 100TB。

## 前置确认（设计有损实验之前必须先问清）

以下两点不确定，会直接改变实验走向，应先向训练同学确认，再投入有损实验：

1. **dataloader 吃压缩态还是解压态。** 如果训练机磁盘上保存的是压缩 TIFF、由 CPU 解码喂 GPU，那“尽量小”指的是磁盘占用，无损压缩就直接有效。如果训练前需要先解压成原始 TIFF 落盘，则无损压缩对峰值占用无帮助，必须靠有损/降分辨率/蒸馏真正减少数据。
2. **是否有共享存储 / 对象存储可流式读。** WebDataset 本就支持 `pipe:` 流式读取（S3 / 共享盘）。如果训练集群能挂远端存储，数据不必落到训练机本地，本地存储约束可被绕过。这是与“压缩”正交的一条路，可能比压缩更省事，应先确认有没有这个条件。

实测补充：在随机抽样的 shard 上，TIFF deflate 的压缩率约为 `45%`（见 `sample_compression_results.md`），明显高于早期单个 test pack 外推的 `24.6%`——压缩率随内容波动很大。按 `45%` 估算，10TB 无损后约 `4.5TB`，而非 `2.5TB`。这进一步说明：在“尽量小”目标下，仅靠无损压缩很可能不够，需要叠加有损方向。

当前 1TB 数据目录为：

`/mnt/huawei_deepcad/webds_micro_100k_by_channel_patched_shuffle`

该目录实际是 packed WebDataset tar shards，总大小约 `966G`，包含 `326` 个顶层 `.tar` shard。样本格式是 `.chN.tif + .meta.json`，TIFF 为 `512x512 uint16` 且当前未压缩。详细检查见 `1tb_dataset_inspection.md`。

## 核心原则

实验需要区分两类方案：

1. 存储压缩：样本集合不变，只改变文件格式、编码、量化、分片和读取方式。目标是节省磁盘并保持训练效果基本不变。
2. 信息压缩：样本集合或分辨率发生变化，例如降采样、patch 选择、feature 去重、聚类采样。目标是减少实际训练信息量，允许有可度量的性能下降。

这两类方案要分开评估。否则 benchmark 下降时无法判断是编解码损失、分辨率损失、样本减少，还是训练 IO 变化导致。

## 主要问题

需要回答四个问题：

1. 同样 1TB 数据，压缩后能省多少存储？
2. 压缩后训练吞吐是否下降，CPU 解码是否成为瓶颈？
3. 在相同训练预算下，DINO 表征质量下降多少？
4. 如果扩展到 10TB 或 100TB，预计需要多少本地磁盘、缓存和读取带宽？

## 实验分层

### 第 0 层：工程可行性实验

目标是先确认压缩数据能不能稳定喂满训练。

对 1TB 数据构建以下版本。结合当前数据格式，第一优先级是“TIFF 内部无损压缩”，而不是 JPEG/WebP：

| 版本 | 样本集合 | 分辨率 | 编码 | 目的 |
| --- | --- | --- | --- | --- |
| Raw | 不变 | 原始 | 原始格式 | baseline |
| TIFF-Deflate | 不变 | 原始 | `.tif` 内部 deflate 无损压缩 | 首选无损压缩候选 |
| TIFF-LZW | 不变 | 原始 | `.tif` 内部 LZW 无损压缩 | 高兼容无损候选 |
| Tar-Zstd | 不变 | 原始 | 外层 `.tar.zst` 或 pipe:zstdcat | 测极限无损压缩率，但需要改读取方式 |
| Tar-LZ4 | 不变 | 原始 | 外层 `.tar.lz4` 或 pipe:lz4cat | 测高吞吐外层压缩 |
| Quantized-8bit | 不变 | 原始 | `uint16 -> uint8` 后再 TIFF deflate | 如果无损仍放不下，再测量化影响 |

每个版本记录：

- 压缩后总大小
- 压缩比
- dataloader images/s 或 samples/s
- GPU utilization
- CPU utilization
- 每 step 数据等待时间
- 单机和多机读取稳定性

吞吐测量两个必须控制的陷阱，否则对比无效：

- **page cache**：第二次读同一份数据可能命中 OS 缓存，使压缩版“看起来”更快。每个版本测前 drop cache 或用够大、不重叠的冷数据，保证冷读对比。
- **CPU:GPU 配比**：deflate / zstd 解码会不会成瓶颈，取决于训练机每块 GPU 配多少 CPU 核。开发机和 7B 训练机的配比通常差很多，**必须在接近 7B 训练机的硬件配比上测吞吐**，开发机结论不可直接外推。

如果某个方案虽然省空间但明显喂不满 GPU，应先淘汰或改成离线分片加本地缓存。

基于 `test_pack_spec` 的初测，TIFF deflate 可以把 TIFF payload 压到约 `24.6%`，LZW 约 `27.2%`。**但随机抽样多个 shard 后，deflate 实测约 `45%`、LZW 约 `56%`**（`sample_compression_benchmark.py`），test pack 偏乐观。正式实验应用该脚本以 `--max-tifs-per-shard 0` 跑 10–20 个 shard 确定数值，不要用 test pack 的数。

#### 重打包的可归因前提

为保证 Raw 与压缩版的 benchmark 差异只能归因于编码，重打包必须满足：

- 样本集合、shard 划分、shard 内顺序完全不变，只把 `dinov3/data/repackage/io_utils.py:60` 的 `compression=None` 改成对应 codec。
- 不重新 shuffle、不重新分片、不丢样本。
- 重打包后抽样 `decode(压缩) == decode(原始)` 校验无损（脚本 `--verify` 已实现）。

#### 量化（Quantized-8bit）必须先定义映射方式

`uint16 -> uint8` 不是一个确定操作，映射方式直接决定质量损失，方案里必须写死并记录：

- 显微数据强度动态范围大、信号常集中在低值区，**naive 全局线性 min/max 量化会把弱信号压没**。
- 候选：per-image min/max、全局 percentile（如 1%–99%）、或 log/gamma 后再量化。至少对比 per-image 与 global-percentile 两种。
- **必须与训练已有的归一化对齐**：`dinov3/data/loaders.py` 已改过归一化逻辑，如果训练本就把像素映射到某个归一化 float 区间，则有效 bit 数的损失要在那个区间里衡量，而不是在原始 uint16 上。
- 量化属于有损，benchmark 评估时要和无损方案分开记录。

### 第 1 层：小模型代理实验

目标是快速估计不同压缩方式对表征质量的影响。

建议先不用 7B，全量跑 7B 成本太高。可以用同架构族的小模型做代理，例如 ViT-S/16、ViT-B/16、ViT-L/16 或当前训练代码支持的最小 DINO 配置。

**重要：不要只用单个 proxy 尺寸外推 7B。** 压缩损失未必跨模型尺度一致——7B 对量化 / 降分辨率可能更敏感也可能更鲁棒。要对“最关心的有损方案”至少跑两个 proxy 尺寸（如 ViT-S 与 ViT-L），观察“压缩相对 Raw 的 benchmark gap 随模型增大是收窄还是放大”。只有 gap 随尺度收窄或持平，才有信心把结论外推到 7B；如果 gap 随尺度放大，必须在 7B 短训上重新验证后才能采用。

固定以下条件：

- 相同 1TB 样本集合
- 相同训练 step 或 token/image budget
- 相同 augment、optimizer、batch size、learning rate schedule
- 相同随机种子，至少关键方案跑 2 个 seed
- 下游 benchmark 使用完全相同的冻结评估协议

推荐先跑以下最小矩阵：

| 组别 | 数据版本 | 训练预算 | 用途 |
| --- | --- | --- | --- |
| A | Raw | 100% | 质量 baseline |
| B | TIFF-Deflate | 100% | 验证无损内部压缩是否等价 |
| C | TIFF-LZW | 100% | 验证兼容性和吞吐 |
| D | Tar-Zstd 或 Tar-LZ4 | 100% | 验证外层压缩读取代价 |
| E | Quantized-8bit + TIFF-Deflate | 100% | 验证量化 |

判断标准：

- 无损压缩：benchmark 应该在随机波动范围内，不应系统性下降。
- 高质量有损压缩：如果主要 benchmark 下降小于 0.2 到 0.5 个点，可进入 10TB 试验。
- 中等有损压缩：如果下降超过 1 个点，需要看节省的存储是否足够值得。

### 第 2 层：分辨率和信息压缩实验

目标是验证“数据变小”是否比“数据压缩”更划算。

在第 1 层中表现最好的编码格式上，再叠加分辨率和采样实验：

| 组别 | 数据量 | 分辨率 | 采样方式 |
| --- | --- | --- | --- |
| R0 | 1TB | 原始 | 原始 |
| R1 | 1TB | 1/2 | 原始 |
| R2 | 1TB | 1/4 | 原始 |
| S1 | 500GB | 原始 | feature 聚类中心样本 |
| S2 | 250GB | 原始 | feature 聚类中心样本 |
| P1 | 1TB 等价 patch budget | 原始 patch | entropy/variance patch |

这里要特别注意：降分辨率、聚类采样和 patch 采样会改变训练分布，不能和纯文件压缩混为一谈。

**与已做的去重的关系需要先澄清。** 1PB → 100/10/1TB 已经做过去重，而 S1/S2 的“feature 聚类中心采样”在概念上与去重重叠。需要和数据侧确认：

- 已做的去重是去“近重复”，而聚类采样是在去重后的集合上进一步下采样（互补），还是
- 二者用同一套 embedding、会重复劳动 / 二次过度删减。

如果去重已经基于 DINO embedding 做过聚类，S1/S2 应复用已有的 embedding 与聚类结果继续下采样，而不是从头再聚一遍；否则可能把已经稀疏的分布进一步破坏。先问清楚再设计这一层。

### 第 3 层：10TB 规模验证

只有当 1TB 实验同时满足以下条件时，才建议上 10TB：

- 压缩后大小能落入训练机器可接受的存储或缓存上限
- dataloader 能稳定喂满 GPU
- 代理模型 benchmark 下降在可接受范围内
- 训练日志中没有明显 loss 异常或 collapse 风险

10TB 试验不需要一开始跑完整 7B。建议分两步：

1. 10TB 数据，代理模型，确认 scaling 曲线是否优于 1TB。
2. 10TB 数据，7B 模型短训，例如 5% 到 10% 训练预算，确认吞吐、loss、特征质量 proxy 指标。

## Benchmark 设计

评估不要只看一个最终指标。建议至少包含：

- 线性探针分类指标
- kNN 或检索指标
- 下游微调指标
- 如果数据包含检测/分割相关目标，增加检测或分割 benchmark
- 表征分布指标，例如 embedding 方差、collapse 检测、nearest neighbor 质量

评估集必须固定，并且不能参与去重、聚类中心选择或压缩参数选择。

## 推荐结论路径

建议按以下决策顺序推进：

1. 先证明 TIFF deflate / LZW 这类无损内部压缩版本与 Raw 训练结果等价。
2. 再比较 TIFF-Deflate、TIFF-LZW、Tar-Zstd、Tar-LZ4 的吞吐，选一个工程上最稳的格式。
3. 如果无损压缩后仍然放不下，再试 `uint16 -> uint8` 量化，看是否能把 10TB 压到训练机器可承载范围。
4. 如果仍然放不下，再考虑分辨率降低、feature 去重和 patch 采样。
5. 最后用 10TB 做代理模型和 7B 短训验证，不建议直接上完整 7B 长训。

## 初始最小实验

如果时间有限，最小实验可以只做 5 组：

| 组别 | 数据 | 目的 |
| --- | --- | --- |
| Raw-1TB | 原始 1TB | baseline |
| TIFF-Deflate-1TB | TIFF 内部无损压缩 | 当前最推荐候选 |
| TIFF-LZW-1TB | TIFF 内部无损压缩 | 兼容性候选 |
| Tar-Zstd-1TB | 外层 tar 压缩 | 测极限压缩率和读取成本 |
| Uint8-Deflate-1TB | 8bit 量化 + TIFF deflate | 验证有损但高压缩方向 |

每组都记录压缩率、吞吐和 benchmark。只有同时看这三者，才能判断是否值得进入 10TB。
